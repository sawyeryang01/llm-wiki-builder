# llm-wiki-builder

> 把一个 skill 变成一套**能长期运转的本地知识库**——你负责找资料和提问，AI 负责写页面、建交叉引用、记账。

一套基于 Andrej Karpathy「LLM Wiki」构想的个人知识库方法论，含**搭建**与**维护**两部分能力，已适配国内环境（Agent 选型、PDF 入库、数据合规）。

---

## 它解决什么问题

所有知识库都死于同一件事：**维护成本的增长速度快于价值增长速度。**

建交叉引用、修订过时结论、标注「A 说 X、B 说 Y」的矛盾、保持几十个页面彼此一致——这些活人干不动，不是因为懒，而是因为**记账**这件事的收益来得太慢。RAG 的方案是把检索做得更聪明，但每次提问都在重新发现知识，什么都没被建立起来。

这个 skill 的解法相反：**把记账外包给 AI**，人只做两件事——丢资料、提问。于是知识会累积：每摄取一篇资料，新结论被编译进已有结构，而不是躺在某个索引里等人来查。

产物是一堆人类可读、可改、可备份、可迁移的 `.md` 文件。不是一个看不见的向量索引，也不依赖任何 SaaS。

## 安装

skill 目录放到用户级目录即可全项目可用：

```
C:\Users\<你>\.workbuddy\skills\llm-wiki-builder\      # Windows
~/.workbuddy/skills/llm-wiki-builder/                  # macOS / Linux
```

从 zip 安装：把 `llm-wiki-builder.zip` 解压到上面的目录（解压后应是 `skills/llm-wiki-builder/SKILL.md`，不要多套一层）。

> **`~/.workbuddy/skills/` 只在应用启动时扫描**——刚放进去不会立刻出现在 skill 列表里，重启后生效。

想装到单个项目里：放到 `<项目>/.workbuddy/skills/llm-wiki-builder/`。

## 快速开始

### 一、建一个新知识库

直接跑脚本：

```bash
python scripts/init_wiki.py D:/my-wiki
```

或者跟 Agent 说：

> 用 llm-wiki-builder 在 `D:/my-wiki` 建一个知识库

脚本会把 `assets/scaffold/` 完整复制过去，写入当天日期，并做一次关键路径自检。

**建完之后有三件事必须做**（`init_wiki.py` 也会在结束时提醒）：

1. 用 Obsidian「打开文件夹作为仓库」打开该目录，**把图谱视图固定到侧边栏**——它是你观察知识结构的仪表盘
2. 把 `AGENTS.md` 交给后续要用的 Agent，让它**先复述规则**再动手
3. 填写 `wiki/综述.md` 的「当前主攻方向」——写清主题边界，AI 才知道哪些资料该收、哪些不该收

第 2 步别省。等它写了一堆页面再纠正，返工代价大得多。

### 二、日常使用

| 你想做什么 | 怎么说 |
|---|---|
| 摄取资料 | `raw/素材/` 里放一篇资料，说「按 AGENTS.md 执行摄取」 |
| 查东西 | 「知识库里关于 X 的记录有哪些？」 |
| 体检 | 「跑一次 lint」/「检查知识库」 |

触发词：**建知识库 / 搭知识库架构 / 第二大脑 / 摄取资料 / 整理入库 / 检查知识库 / lint / 体检**。

### 三、校验已有知识库

```bash
python scripts/lint_wiki.py D:/my-wiki
```

只读，不改任何文件。检查 frontmatter 合法性、BOM、空链接、孤儿页面、`index.md` 统计是否与实际吻合。

## 三层架构（不可动摇）

| 层 | 位置 | 谁写 | 性质 |
|---|---|---|---|
| **Schema** | `AGENTS.md` | 人机共维护 | 行为说明书。定义页面类型、建页门槛、工作流、格式规约 |
| **Raw** | `raw/` | **只有人** | 事实来源。只进不改，AI 只读 |
| **Wiki** | `wiki/` | **只有 AI** | 结构化知识。人只读 |

权限严格隔离是这套方法成立的根基：`raw/` 只读 → 事实不被篡改；`wiki/` 独占写 → 一致性不被人手改坏。

**你几乎不手写 wiki。** 你只做两件事：往 `raw/` 放资料，提问。

## 建库后会得到什么

```
<知识库根目录>/
├── AGENTS.md          【核心】给 AI 的行为说明书（Schema 真源）
├── CLAUDE.md          ┐ 副本，供 Claude Code 读取
├── QWEN.md            ┘ 副本，供 Qwen Code 读取
├── README.md          使用说明（面向使用者）
├── 方法论.md           原理、国内改造、工具选型、九个坑
├── 操作指令.md          可复制指令库 + 各 Agent 接法 + 排错
├── index.md           内容索引（AI 每次操作后更新）
├── log.md             操作日志（只追加）
├── .gitignore         已排除 raw/私有/ 与运行时目录
├── .obsidian/         预置配置（附件目录、排除规则、模板路径）
├── templates/         来源 / 实体 / 概念 / 对比 四套页面模板
├── raw/               你的资料池（AI 只读）
│   ├── 素材/          文章、报告、PDF 转出的 md
│   ├── 图片/          截图、图表、扫描页
│   ├── 归档/          已处理完的原始资料
│   └── 私有/          ⚠️ 敏感资料，只允许本地模型处理（已 gitignore）
└── wiki/              AI 维护的知识（你只读）
    ├── 综述.md         当前主攻方向 + 主题地图
    ├── 待建概念.md      排队中的概念（防过度抽象）
    ├── 来源/           每篇资料一篇摘要
    ├── 实体/           人 / 公司 / 产品 / 机构 / 标准 / 项目
    ├── 概念/           原理 / 方法 / 术语 / 技术路线
    └── 对比/           跨来源综合：方案对比、路线选型、立场分歧
```

## 本 skill 的目录

```
llm-wiki-builder/
├── SKILL.md                        主流程：三层架构 + 搭建 6 步 + 维护三操作 + 9 个坑
├── scripts/
│   ├── init_wiki.py                部署脚手架（复制 + 日期替换 + 23 项自检 + 冲突预检）
│   └── lint_wiki.py                一致性校验（纯只读）
├── references/
│   └── document-ingestion.md       PDF / 扫描件 / 网页 / 微信转 Markdown 的实操与校验
└── assets/scaffold/                完整脚手架（26 个文件，随 init_wiki.py 整体复制）
```

### `init_wiki.py`

```bash
python init_wiki.py <目标目录> [--date YYYY-MM-DD] [--force]
```

| 参数 | 说明 |
|---|---|
| `<目标目录>` | 将成为知识库根目录，不存在会自动创建 |
| `--date` | 写入 frontmatter 的日期，默认取系统当天 |
| `--force` | 覆盖目标目录中已存在的同名文件 |

**冲突预检**：不带 `--force` 时，目标目录里只要有一个同名文件，脚本就**整体中止、不动任何东西**，并列出冲突清单。不会出现「复制到一半」的中间状态。

退出码：`0` 成功 / `1` 有冲突 / `2` 找不到脚手架 / `3` 自检发现缺失路径。

### `lint_wiki.py`

```bash
python lint_wiki.py <知识库根目录>
```

检查 6 项：页面清单 · frontmatter 是否存在且合法 · 是否带 BOM · 空链接 · 孤儿页面 · `index.md` 统计核对。

**零写操作**（纯只读）。`pyyaml` 为可选依赖，未安装时降级为结构检查。

> 它只做**能确定判断**的检查。「两个页面说法矛盾」「结论被新资料推翻但未标注」这类需要人类裁决的问题，由 Agent 在 Lint 流程里列清单报告，不擅自改。

## 面向国内的四处改造

Karpathy 原方案假设 macOS + Obsidian + Claude Code + 全部资料可上云。直接照搬会踩四个坑：

| 环节 | 原方案 | 本 skill 的替换 | 为什么 |
|---|---|---|---|
| **Agent** | Claude Code | Qwen Code / 国产 Coding Plan / 手边任意 Agent | 原方案要外币卡 + 代理；国产模型能力已够，价格低一个数量级 |
| **Schema 文件名** | `CLAUDE.md` | **`AGENTS.md`**（另存 `CLAUDE.md` / `QWEN.md` 副本） | 换个工具就失效。以 `AGENTS.md` 为真源，改完必须同步三份 |
| **同步** | Obsidian Sync | 坚果云 WebDAV / Gitee 私有仓库 | 不需要代理。**别用 OneDrive 直连**，同步冲突会毁掉 AI 维护的一致性 |
| **PDF 入口** | 无 | **MinerU**（上海 AI Lab 开源） | 国内知识密度大头是政策文件、白皮书、招标文件的 PDF |

**第五条改造是原方案完全没提、但对国内用户是硬约束的：数据合规。**

`raw/` 里很可能有客户名称、报价、投标文件、项目图纸——交给云端模型可能直接构成违约。所以脚手架预置了 **`raw/私有/` 公私分层**：公开资料走云端模型，私有资料只用本地模型（Ollama / vLLM 跑 Qwen、DeepSeek 开源版），该目录已写入 `.gitignore`，不会同步到任何远端。

**这一条是在摄取第一篇资料之前就要建好的。** 详细规则见脚手架内的 `方法论.md` 与 `AGENTS.md` 第 7 节。

---

## 九个常见的坑

1. **把 wiki 当收藏夹。** 只进不出、只存不整合。检验标准就是图谱里有没有新连线。
2. **一次吞十篇。** 人类会失去掌控感，AI 也会跳过讨论环节。一次一篇。
3. **没配版本控制就开干。** AI 一次能改十几个文件，先上 Git 或 WebDAV。
4. **把 schema 文件叫 `CLAUDE.md`。** 换个工具就失效。以 `AGENTS.md` 为准。
5. **让 AI 自动「裁决」矛盾。** 不行。矛盾只标注、不裁决，判断权归人。
6. **删掉过时结论。** 用 `> ⚠️ 已被 [[新来源]] 更新：原说法为……` 标注。认知演进本身就是知识。
7. **没有公私分层。** 见上一节，这是硬约束。
8. **指望第一次就搭对。** Schema 是磨出来的，不是设计出来的。用一周再改它。
9. **以为需要向量库。** 100 篇资料、几百个页面的规模下，一个维护良好的 `index.md` 就够用。别提前优化。

## 维护说明

**这套方法的规约不在本 skill 里，在你自己知识库的 `AGENTS.md` 里。**

skill 的维护流程刻意**不复述**那套规则（只写「动手前必须先完整读目标库的 `AGENTS.md`」）——两处都写规则，将来一定会漂移。要改规约，改你的 `AGENTS.md`，不是改这个 skill。

同理，**这个 skill 的脚手架不是一次性设计出来的**：它的规则来自一次真实的摄取（3 篇招投标文件 → 10 个页面），`AGENTS.md` 的建页门槛、`index.md` 的统计格式、`lint_wiki.py` 的检查项都是被那批真实资料逼出来的。你在用的时候如果发现它不合手，那很正常——改它。
