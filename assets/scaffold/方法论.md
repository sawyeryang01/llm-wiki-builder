# 方法论：LLM Wiki 为什么有效，以及国内怎么落地

> 基于 Andrej Karpathy 2026 年 4 月发布的「LLM Wiki」构想（gist: `karpathy/442a6bf555914893e9891c11519de94f`）。
> 本文说明原理、和 RAG 的本质差别、面向国内的四处改造、工具选型，以及常见的坑。
> 日常操作指令见 `操作指令.md`；给 AI 的规约见 `AGENTS.md`。

---

## 一、30 秒版本

**核心一句话**：别再"每次提问都把资料重粘一遍"，让 AI 帮你维护一本会自己变厚的知识手册。

```
你：找资料 → 丢进 raw/ → 提问
AI：读资料 → 提炼 → 建档 → 更新交叉引用 → 标注矛盾 → 记账
```

日常就是三件事：**摄取（Ingest）· 查询（Query）· 体检（Lint）**。

Karpathy 自己的研究 wiki 是 100 多篇文章、40 万字，他一个字都没手写。

---

## 二、它和 RAG 到底差在哪

这一节很重要，因为国内大部分"知识库"产品走的都是 RAG 路线，方向不对。

| 维度 | 主流 RAG（NotebookLM、上传文件问答、多数向量库方案） | LLM Wiki |
|---|---|---|
| 知识是否累积 | ❌ 不累积。每次查询都从原始文档重新拼一遍 | ✅ 持续累积，越用越厚 |
| 产物形态 | 一个你看不见的向量索引 | 一堆你能读、能改、能备份的 `.md` 文件 |
| 矛盾处理 | 发现不了 | 主动标注"A 说 X，B 说 Y" |
| 综合结论 | 每次重新生成，每次可能不一样 | 编译一次，之后持续维护 |
| 维护成本 | 高（靠人不定期重新上传） | 趋近于零（AI 全权记账） |
| 可审计性 | 黑箱 | 每条结论都能追溯到具体的 md 文件和原始资料 |

Karpathy 原话点破了问题的本质：

> **维护知识库累人的地方，不是读、不是想，是记账。**
> 更新交叉引用、让摘要不过时、标注新数据推翻了哪个旧结论、在几十个页面之间保持一致性——
> 人不做这些事，不是懒，是因为**维护成本的增长速度快于价值增长速度**。
> 人类放弃 wiki，都是这么放弃的。

LLM 恰好擅长这个：它不会无聊，不会忘记更新一个引用，可以一次改 15 个文件还保持一致。

**所以这套方法的杠杆不在"更强的检索"，而在"把记账外包出去"。**

## 三、三层架构

| 层          | 位置          | 谁写         | 性质                                                                 |
| ---------- | ----------- | ---------- | ------------------------------------------------------------------ |
| **Schema** | `AGENTS.md` | 你和 AI 共同维护 | 行为说明书。定义页面类型、工作流、格式规约。**这是整套方法的关键文件**——它让 AI 从"通用聊天机器人"变成"有纪律的维护者" |
| **Raw**    | `raw/`      | **只有你**    | 事实来源。文章、报告、图片、数据。**只进不改**，AI 只读                                    |
| **Wiki**   | `wiki/`     | **只有 AI**  | 结构化知识。摘要页、实体页、概念页、对比页。你只读                                          |

**读写权限严格隔离**，这是整个设计能成立的根基：

- `raw/` 只有你能写 → 保证事实来源不被 AI 篡改
- `wiki/` 只有 AI 写 → 保证你不会手改坏它维护的一致性

两个特殊文件也很关键：

- **`index.md`** — 内容索引。AI 每次摄取后更新。查询时先读它定位，再深入具体页面。**在 100 篇资料、几百个页面的规模下，一个维护良好的索引就够用了，不需要向量库。**
- **`log.md`** — 操作日志，只追加。每行用固定前缀，于是可以这样查：
  ```bash
  grep "^## \[" log.md | tail -10
  ```

## 四、面向国内，必须改造的四件事

Karpathy 的原始方案假设你在 macOS + Obsidian + Claude Code，且所有资料都能交给云端。国内直接照搬会踩四个坑。

### 改造 1：Agent 层换成国内可直连的

Karpathy 用的是 Claude Code，国内需要外币卡 + 代理。**没必要。** 现在国产模型的能力已经够用，而且价格便宜一个数量级。

关键点：**这套方法要求 Agent 能读写本地文件夹**，所以必须选带文件操作能力的 Agent，不能是纯网页版对话框（网页版看不到你的 `raw/` 目录）。

**两条路线：**

**路线 A（推荐）**：国产订阅 + 支持自定义接口的 CLI

- 智谱 GLM Coding Plan、阿里云百炼 Coding Plan、Kimi Code Plan、MiniMax、火山方舟、腾讯云 Coding Plan 等，部分原生支持 Anthropic 协议，可以直接驱动 Claude Code（本体现在免费，只需一个兼容端点）
- 国产 CLI：**Qwen Code**（阿里开源，Apache-2.0，支持 Ollama 本地模型）、OpenCode、Cline / Roo Code（VS Code 插件）、Trae / CodeBuddy（IDE 内置 Agent）

**路线 B（最省事）**：用你手边这个工具本身。当前对话所在的 WorkBuddy 就能直接读写本地文件夹、在这个知识库上工作，国内直连、不需要任何配置。

> **Schema 文件统一命名 `AGENTS.md`**。
> Karpathy 原文写的是 `CLAUDE.md`（Claude Code 专用）。但 Codex 读 `AGENTS.md`、Qwen Code 读 `QWEN.md`、Claude Code 读 `CLAUDE.md`——换个工具就失效。
> 本库的做法：以 `AGENTS.md` 为准，另存 `CLAUDE.md` 和 `QWEN.md` 两份副本。改 `AGENTS.md` 后记得同步。

### 改造 2：前端与同步

| 环节 | 国内方案 | 说明 |
|---|---|---|
| **Markdown 前端** | **Obsidian**（免费个人版，本地，不锁定） | 国内可直接下载。图谱视图是看知识结构的最佳方式 |
| | **思源笔记 SiYuan**（国产开源） | 本地优先，内置块引用、免费 WebDAV 同步，中文生态更贴 |
| **同步** | **坚果云 WebDAV** + Obsidian `Remotely Save` 插件 | 国内最常用的免费方案，无需代理 |
| | **Git + Gitee 私有仓库** | 本库已是 git 仓库。免费拿到版本历史、分支、回溯 |
| | 群晖 / 威联通 NAS + Syncthing | 数据完全自持，适合敏感资料多的人 |

⚠️ **不要把整库放在 OneDrive / iCloud 里让 Obsidian 直接读写**——同步冲突会毁掉 AI 维护的一致性。

### 改造 3：信息源层要按国内的来

Karpathy 的 raw 入口是 Obsidian Web Clipper。国内的信息源结构完全不同，需要补三个入口：

**① 微信公众号文章**（国内知识密度最高的信源，但剪藏最难）

- 微信读书 → 划线笔记导出
- 公众号内容订阅工具转 RSS，再用通用剪藏器抓取
- 反爬严重的，直接在手机里复制正文，粘贴成 md 存进 `raw/素材/`

**② PDF 与扫描件**（政策文件、白皮书、招标文件、行业报告）

- **MinerU**（上海人工智能实验室 OpenDataLab 开源）是当前最合适的选择：PDF / 扫描件 / Word / PPT / Excel / 图片 → 干净 Markdown，公式表格识别率高，有 MCP 接口可被 Agent 直接调用，也有免鉴权的 Agent 通道
- 用法：把 PDF 丢给 MinerU 转成 md，再放进 `raw/素材/`——**这一步能把大量"死文档"变成 AI 可读的原料**，是国内方案里性价比最高的一环

**③ 图片与截图**

- 附件目录已预置为 `raw/图片/`
- 再给「下载当前文件的附件」绑个快捷键（如 `Ctrl+Shift+D`）。剪藏后按一下，所有图片落到本地，AI 就能用视觉能力引用它们
- 注意：AI 没法一次性读"图文混排的 md"，得让它先读文字，再单独看图片补充上下文。有点笨但能跑

### 改造 4：数据合规（**国内方案最重要的一条**）

这一条 Karpathy 完全没提，但对政企从业者是硬约束。

**问题**：`raw/` 里很可能有客户名称、报价、投标文件、项目图纸、未公开的合同。把这些交给云端大模型，可能构成违约甚至违规。

**解决：公私分层。** 本库已经建好 `raw/私有/`，具体做法：

1. **已加入 `.gitignore`**，不会被同步到任何 Git 远端
2. **只用本地模型处理**：Ollama 或 vLLM 跑开源模型（Qwen、DeepSeek、GLM 系列都有可本地部署的版本）。Qwen Code 支持直连 Ollama 本地端点，同一套 Agent 工作流可以无缝切换
3. **确需云端分析时先脱敏**：客户名换代号（"某市供电公司 A"），删掉报价数字和联系方式
4. **结论也要脱敏**：写进 `wiki/` 的页面里同样不出现真实客户名，代号与真名的对应关系单独存在密码管理器里
5. **来源页 frontmatter 加 `tags: [私有]`**，方便日后审计

| 环节 | 推荐 | 备选 | 备注 |
|---|---|---|---|
| **Agent 本体** | 当前对话工具 / Qwen Code | OpenCode、Cline、Roo Code、Claude Code（配国产兼容端点） | 硬要求：能读写本地文件夹 |

## 六、页面类型与建页规则

| 类型 | 建页时机 | 背后的道理 |
|---|---|---|
| **来源** | 每篇资料必建 | 每篇资料都需要可追溯的落点 |
| **实体** | 首次被独立段落讨论就建 | 人/公司/产品单篇就能刻画清楚，不必等 |
| **概念** | **被 2 篇以上来源提到才建** | 概念最容易过度抽象变成空壳，先攒证据 |
| **对比** | 2 篇来源立场不同，或查询时产生新分析 | 对比是最有价值的产出，也最容易被丢掉 |

**核心原则：自下而上，不要急着抽象。**

只出现一次的术语，先在来源页里写成 `[[某概念]]` 留个空链接，同时记进 `wiki/待建概念.md` 排队。等它第二次出现，再正式建页并回头补链接。

这个"缓冲池"机制能有效防止你的库变成一堆空壳概念页。模板见 `templates/`。

## 七、九个常见的坑

1. **把 wiki 当收藏夹用。** 只进不出、只存不整合。检验标准：看图谱，有没有新连线。
2. **一次吞十篇。** 会失去掌控感，AI 也会偷懒跳过讨论环节。**一次一篇，保持参与。**
3. **不配上版本控制就开干。** AI 一次能改 15 个文件，改错了没有历史会很痛苦。**先上 Git 或 WebDAV。**
4. **指望 AI 一次性读图文混排的 md。** 它做不到。让它先读文字，再单独看图片。
5. **把配置文件叫 `CLAUDE.md`。** 换个工具就失效。用 `AGENTS.md`。
6. **让 AI 自动"裁决"矛盾。** 不行。矛盾只标注、不裁决——判断权必须在人手里。
7. **删掉过时结论。** 不要删。用 `> ⚠️ 已被 [[新来源]] 更新：原说法为……` 标注。**认知演进的过程本身就是知识。**
8. **没有公私分层。** 客户资料进了云端模型，可能是违约。**先建 `raw/私有/`，再开始摄取第一篇资料。**
9. **指望第一次就搭对。** Schema 是磨出来的，不是设计出来的。用一周，然后改它。

## 八、规模与成本

| 项 | 成本 |
|---|---|
| Obsidian / 思源 / MinerU / Git | 免费 |
| 坚果云 WebDAV | 免费档够用 |
| 模型订阅 | **约 ¥20–100/月**（国产 Coding Plan） |
| 本地模型电费 | 可选，看硬件 |

**关于规模**：Karpathy 说他的方案在约 100 篇文章、40 万字的规模下明显优于传统 RAG，而且**完全人类可读、可审计、摆脱供应商锁定**。

这个"不需要向量库"的结论对国内用户尤其友好——不用维护 Milvus / Elasticsearch，不用调 embedding 模型，不用调分块策略。**一个维护良好的 `index.md` 就够了。**

什么时候需要加检索？大概到几百个页面以上，再考虑 `qmd` 这类本地 markdown 检索工具（有 MCP 接口，能被 Agent 直接调用）。到那之前，别提前优化。

## 九、这个想法的来处

Karpathy 把它关联到 Vannevar Bush 1945 年的 **Memex** 设想——一个私人的、主动策划的知识存储，文档之间的**联想路径和文档本身一样有价值**。

> Bush 想清楚了愿景，但留了一个没解决的问题：**谁来做维护？**
> 维护成本最终压垮了每一个 wiki，也让 Memex 停留在设想里。
> LLM 补上的正是这一步。
